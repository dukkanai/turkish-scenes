- حفظ ذري مستقل ونسخة سابقة وحماية من الكتابة فوق ملفات فاسدة؛ لا تسجيل للصوت أو نص الإجابات.
- مفتاح شخصي في Keychain، واتصال WebSocket مباشر بالنموذج المحدد، وموافقة جلسة مدفوعة وحد زمني وكتم وإيقاف.
- واجهة عربية ووسوم نطق تركية، وتوقف عند الخلفية والمقاطعات وفصل سماعات.

## تشخيص رفض Realtime بعد تسليم 11.1

رسالة الرفض في 11.1 كانت تجمع كل أحداث `error` في نص واحد عن المفتاح والرصيد والنموذج، دون الاحتفاظ برمز الخطأ أو الحقل. هذا خلل تشخيص مؤكد، ولا يثبت سبب رفض حساب المستخدم. الاسم `gpt-realtime-2.1` وعنوان WebSocket وصيغة PCM 24kHz وصوت marin موثقة حاليًا في [مرجع OpenAI](https://developers.openai.com/api/reference/resources/realtime/client-events) و[دليل WebSocket](https://developers.openai.com/api/docs/guides/voice-websockets).

أزيل حقل model الزائد من session.update لأن اختيار النموذج يتم عند الاتصال ولا يمكن تغييره أثناء الجلسة؛ لا يُدّعى أنه السبب المؤكد لواقعة الرفض دون رمزها. أضيف عرض آمن لرمز/نوع الخطأ والحقل من قوائم ثابتة، ومرحلة الخطأ ورموز HTTP المعروفة، بدل افتراض خلل المفتاح أو الرصيد. لا يُعرض أو يُسجّل نص الخطأ الخام أو الطلب أو المعرفات؛ قد تتضمن أسرارًا. تشمل الاختبارات حالة خطأ إعداد الطلب والرصيد وحد المعدل وحقن بيانات خاصة في جميع حقول الخطأ. هذه التعديلات قيد CI والتسليم، وليست بعد ضمن 11.1. لم تُنفذ أي مكالمة API في هذا التحقيق.

## مراجعة رفض حقل threshold

في مراجعة 2026-11-07، كان رأس الفرع `b02a72f6fb41fbb01fd0333b5d0b448cce19041a`. بلّغ المستخدم رفض تهيئة الجلسة بالنوع `invalid_request_error` والحقل `session.audio.input.turn_detection.threshold`. الكود أرسل `server_vad` وقيمة 0.6؛ [دليل VAD الرسمي](https://developers.openai.com/api/docs/guides/realtime-vad) ما زال يصف هذا الحقل والقيم بين 0 و1، لذلك لا تثبت الأدلة سبب الرفض الدقيق أو وجود مشكلة في المفتاح أو الرصيد.

استُبدل إعداد كشف الدور بأبسط صيغة `semantic_vad` الواردة في [دليل محادثات Realtime مع gpt-realtime-2.1](https://developers.openai.com/api/docs/guides/realtime-conversations)، دون حقول عتبة أو مدد خاصة بـserver VAD. هذا اختبار توافق موثق، وليس ادعاء نجاح اتصال حي. اختبار Swift يقارن حدث session.update الذي يستخدمه التطبيق فعلًا، بعد تحويله إلى JSON، بشكل متوقع كامل، ويرفض إعادة حقول server VAD إلى هذا الإعداد.

كشفت المراجعة أيضًا أن الردود المقاطَعة كانت تُستبعد قبل جمع استهلاكها. أصبح الاستهلاك المُبلّغ من API يُجمع قبل تجاهل مخرجات الرد المقاطَع، مرة واحدة لكل معرف رد، دون قبول تقييمه أو تشغيل صوته المتأخر. أضيفت اختبارات الرد الملغى والفاشل وغير المكتمل، التكرار، القيم غير الصالحة وتصفير الجلسة. العدد ليس تقدير فاتورة نقدية، وقد لا يشمل استهلاكًا لم يُبلغ قبل قطع الاتصال.

نجحت 13 حالة Python وفحص صياغة Bash و`git diff --check` محليًا. لا تتوفر Swift أو Ruby أو Xcode في هذا المنفذ؛ الفحوص المترجمة وبناء iOS وفحص الواجهة والأرشفة والتسليم تنتظر مسار GitHub macOS على commit المرشح. لم تُستخدم مفاتيح أو استدعاءات OpenAI مدفوعة في التحقيق، ولا تُعد هذه الفقرة إثبات إتاحة نسخة جديدة في TestFlight.

## إصلاح توقف الجلسة بعد رد غير مكتمل

أفاد المستخدم بعد تجربة 14.1 بأنه يسمع جملة ثم تظهر رسالة الرد غير المكتمل وتتوقف الجلسة. في المصدر `cb0de493c9dadfff67f519507731380c9e51bad1`، كان فرع `response.done` لحالة `incomplete` يستدعي `stop`؛ وهذا يغلق الاتصال والميكروفون ويمسح الصوت الموجود في طابور التشغيل. هذا عيب مؤكد في دورة حياة التطبيق، لكنه لا يثبت سبب عدم اكتمال رد OpenAI نفسه.

بحسب [مرجع أحداث الخادم](https://developers.openai.com/api/reference/resources/realtime/server-events)، `response.done` يعني انتهاء توليد الرد، وقد تكون حالته مكتملة أو ملغاة أو فاشلة أو غير مكتملة. السببان الموثقان للحالة الأخيرة هما `max_output_tokens` و`content_filter`. أما المقاطعة الصوتية وإلغاء العميل فهما سببان لحالة `cancelled`. وبحسب [مرجع أحداث العميل](https://developers.openai.com/api/reference/resources/realtime/client-events)، يصل الصوت أسرع من تشغيله، وحد الرد يشمل المخرجات والأدوات؛ لا يجوز تفسير نهاية التوليد على أنها انتهاء تشغيل الصوت.

التعديل يبقي الجلسة وطابور الصوت والكتم والمهلة كما هي عند الرد غير المكتمل، ويعرض سببه من قائمة ثابتة أو يقول إن السبب غير معروف. لا ينفذ أدوات أو يحسب إتقانًا من رد غير مكتمل أو ملغى، ولا يرسل طلب استمرار تلقائيًا. يبقى الاستهلاك المُبلّغ محسوبًا. تظل الأخطاء الحقيقية وقطع الشبكة وانتهاء المدة والخلفية والإيقاف اليدوي أسبابًا لإغلاق الجلسة.

بقي `max_output_tokens=700` دون زيادة أو إزالة الحد. عُدلت تعليمات الشرح لعنصر واحد ومثال قصير في كل دور ثم انتظار المتعلم، بدل طلب عناصر الدرس الخمسة في رد واحد. بلوغ الحد تفسير محتمل فقط إلى أن يصل `status_details.reason` من التجربة الفعلية. أضيفت اختبارات أحداث JSON للسببين الموثقين والسبب المفقود والمزيف، والإلغاء والفشل وتعاقب الأدوار، مع فحص ربط مسار التطبيق لحماية الصوت والتقدم وعدم إنشاء طلب مدفوع تلقائي. الفحوص الحية لا تزال غير منفذة؛ لا ادعاء بإصلاح مؤكد على الجهاز قبل تجربته.
