# خطة GitHub والبناء والتوزيع

هذه وثيقة إجراءات للبناء والتوزيع لاحقًا. بعد كتابة الخطة أُنشئ المستودع العام [dukkanai/turkish-scenes](https://github.com/dukkanai/turkish-scenes) بإذن المستخدم، ثم أذن برفع ملفات المشروع الحالية. لم يُنشأ workflow أو إعداد Apple؛ راجع [الحالة الحالية](EXECUTION_STATUS.md).

## المستودع

الاسم `turkish-scenes`، والحساب `dukkanai`، والظهور عام كما طلب المستخدم. تُرفع الوثائق ومصدر المحتوى الحالي وفق طلبه؛ لا تُضمّن إعدادات البيئة المحلية `.codex` أو بيانات التوقيع أو ملفات تقدم شخصية أو نواتج البناء. لم يُضف ترخيص للكود أو المحتوى؛ علنية المستودع وحدها لا تمنح ترخيصًا لإعادة الاستخدام.

البنية المقترحة: مشروع Xcode واحد، مجلد تطبيق، مجلد اختبارات، مجلد محتوى، أداة تحويل، الوثائق الحالية، ومجلد workflows لاحقًا. لا يُنشأ أي منها كتنفيذ في هذه المرحلة.

## CI المقترح

| المسار | التشغيل | العمل |
| --- | --- | --- |
| فحص التغييرات | pull request وpush للفرع الرئيسي | تحقق المحتوى، بناء المحاكي، اختبارات منطقية وواجهة أساسية، حفظ تقرير مختصر |
| إصدار TestFlight | تشغيل يدوي من فرع/وسم موثوق | الاختبارات، الأرشفة والتوقيع، رقم build فريد، التحقق والرفع، ثم تسجيل معالجة Apple |

يُثبّت إصدار runner وXcode المتاح والمقبول عند التنفيذ؛ لا يُكتب `latest` دون معرفة ما اختُبر. إلغاء التشغيلات القديمة لنفس PR يقلل وقت CI. لا يرفع كل PR نسخة TestFlight ولا يحصل على أسرار Apple.

تكون صلاحيات CI للقراءة افتراضيًا وتزاد عند الحاجة فقط. لا ينفذ كود PR خارجي في سياق يملك أسرار الإصدار، ولا يُستخدم `pull_request_target` لبناء ذلك الكود. تُثبت إصدارات الإجراءات المستخدمة وتراجع قبل تغييرها. [توثيق GitHub للأمان](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

## أدوات البناء ودعم النظام

الحد الأدنى للتشغيل iOS 16.0، وهو مستقل عن إصدار SDK المستخدم للبناء والرفع. عند التحقق بتاريخ 2026-11-01 كانت صفحة Apple تذكر Xcode 26 أو أحدث لبناء تطبيقات iOS المرفوعة؛ تُراجع المتطلبات مجددًا عند تجهيز الإصدار، دون تغيير حد التشغيل الأدنى تلقائيًا. [متطلبات رفع Apple](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds/)

## المعلومات المطلوبة لاحقًا

| المعلومة | متى ولماذا |
| --- | --- |
| حساب/منظمة GitHub | عند إنشاء المستودع العام |
| Apple Team ID وBundle ID فريد | إعداد هوية التطبيق والتوقيع وتعريف هوية مشغل YouTube |
| سجل التطبيق في App Store Connect | ربط النسخ المرفوعة بالتطبيق |
| طريقة التوقيع وشهادة التوزيع وملف provisioning عند الحاجة | إنشاء archive قابل للتوزيع |
| مفتاح App Store Connect المناسب ومعرفه وIssuer ID عند الحاجة | أتمتة الرفع المصرح به |
| مجموعة المختبرين | توزيع نسخة TestFlight؛ الحساب موجود لدى المستخدم |
| إصدار iOS الفعلي على XS Max | توثيق نتائج التجربة |

لا تُطلب المفاتيح الخاصة في محادثة أو ملف عام. تُضاف مباشرة إلى GitHub Secrets/بيئة الإصدار بالطريقة المناسبة عند التنفيذ. تُنشأ keychain مؤقتة على runner وتُنظف بعد الاستخدام. لا تطبع المفاتيح أو الشهادات أو ملفات التوقيع في السجلات، ولا تُرفق كـartifacts.

## استلام TestFlight

1. نجاح CI وأرشفة نسخة برقم متزايد.
2. رفع النسخة وظهورها بعد معالجة Apple؛ نجاح أمر الرفع وحده ليس استلامًا.
3. استكمال معلومات الاختبار المطلوبة لدى Apple؛ الاختبار الخارجي قد يحتاج مراجعتها.
4. إتاحة النسخة للمجموعة المقصودة وتثبيتها على هاتف المستخدم.
5. تجربة التعلم والكتابة والاختيارات والخطأ والمراجعة والإغلاق وإعادة الفتح مع VoiceOver.
6. توثيق الإصدار ونتائج القبول وإصلاح العيوب قبل ترشيح نسخة المتجر.

## تجهيز النشر النهائي

- اسم ووصف وكلمات مفتاحية وأيقونة وصور تعكس التطبيق الفعلي، وملاحظات مراجعة تشرح استخدام YouTube.
- عنوان دعم وسياسة خصوصية منشورة يعكسان السلوك الفعلي. التقدم محلي، لكن المشغل يتصل بـYouTube؛ لا توصف التجربة بأنها بلا أي اتصال أو مشاركة بيانات مع طرف ثالث.
- مراجعة إفصاحات الخصوصية ومتطلبات SDK والتصنيف العمري والمحتوى وحقوق توزيع النصوص وفق الحالة الفعلية، دون اختلاق موافقات.
- حسم سعر المتجر وترخيص الكود؛ لا توجد منظومة شراء ضمن نطاق التطبيق المخطط.
- نسخة مرشحة اجتازت TestFlight وخطة إصلاح لاحق. إرسال المتجر لا يضمن قبول Apple.

## صيانة المحتوى والإصدارات

قبل كل فيلم جديد: تدقيق الرابط والمصدر، تحويل ومراجعة الأسئلة، اختبار تشغيل العينات، إضافة معرفات ثابتة، واختبار تحديث فوق نسخة تحتوي تقدمًا. لا يُستبدل ملف تقدم المستخدم بملف افتراضي.

إذا ظهر خلل بعد التوزيع: يُوقف توزيع النسخة التجريبية المتأثرة عند اللزوم، ويصدر إصلاح برقم build جديد. الرجوع إلى كود أقدم لا يبرر خفض مخطط التخزين أو فقد البيانات. تُختبر قراءة البيانات قبل توزيع أي إصلاح.
